## 1. 结构 (Structural)

### 类型

教材型方法论 —— 以统一过程（UP）为流程骨架、以两个贯穿式案例（NextGen POS、Monopoly）为载体的面向对象分析与设计教科书。不是"模式目录"，也不是"UML 手册"（作者反复强调这一点）。

### 一句话主旨

**用一组可命名的原则（GRASP）在迭代演进中给对象分配职责，从而把面向对象设计从"凭直觉的手艺"变成"可教学、可论证、可复用"的工程实践。**

### 骨架 (主要论点及其关系)

1. **对象设计的实质是职责分配，不是画图**。用 RDD（职责驱动设计）隐喻取代"数据结构+算法"隐喻：软件是一群有职责的对象在协作。UML 只是表达工具，"受过设计原则训练的头脑"才是真正的设计工具（17.1）。
2. **职责分配有可命名、可学习、可论证的原则 —— GRASP 九模式**。Creator / Information Expert / Low Coupling / Controller / High Cohesion（Ch17）+ Polymorphism / Pure Fabrication / Indirection / Protected Variations（Ch25）。作者明说模式名字不重要，重要的是它们逼你**对每一步决策给出理由**（18 章 "No-Magic Zone"）。
3. **领域模型是灵感来源，不是设计蓝图**。概念视角 ≠ 软件视角（9.2）；没有"唯一正确"的领域模型（9.18）；最常见的错误是**把本该是概念类的东西建模成属性**（9.12）；用 Description 类描述"一类事物的描述"而非实例（9.13）。
4. **GoF 模式是 GRASP 原则的特化，GRASP 是上位抽象**。Adapter = Indirection + Protected Variations（26.2）；一句"用 Abstract Factory 生成的 Strategy 来支持对 X 的 Protected Variations"能压缩传递一整块设计意图（25 章导言）。
5. **架构层面：先识别变化点与演化点，再把非功能需求显式化为架构因素表，最后做权衡取舍**。作者区分"科学"与"艺术"：收集整理因素是科学，权衡取舍是艺术（33.7）。Layers 定大块，Facade/Controller/Observer 定块间协作（34.2）。
6. **一切都发生在迭代里，而且早期要故意"挑动变化"**。设计与实现阶段的早期编程/测试/演示，是为了把不可避免的需求变更**提前引爆**，让后期迭代目标稳定（12.2）。架构是渐进演化的，不做前期大规模推测式设计（34.1）。
7. **框架级设计=模式组合**。以持久层为例：Template Method 固化算法骨架、State 管事务状态、Command 封装事务、Virtual Proxy 做延迟物化、RDBOperations 做 Pure Fabrication 收拢 SQL（Ch38）。

**论点之间的关系**: 递进 + 包裹。1–3 是对象级基本功，4 把抽象层级抬高一档，5 放大到系统级，6 是贯穿全部的过程观（每个论点都在迭代语境下成立），7 是综合应用案例。

### 作者要解决的核心问题

> 新手和有经验的开发者在做 OO 设计时，面对"这个方法该放哪个类""对象之间该怎么交互"这些问题只能靠模糊直觉——怎么把这种决策变成**有名字、有理由、可讨论、可传授**的东西？

作者的答案：给原则命名（GRASP），把设计过程变成可解释的推理链，而不是审美判断。

## 2. 解释 (Interpretive)

### 关键术语 (作者本人的用法)

| 术语 | 作者的定义 | 和常识用法的差异 |
|---|---|---|
| **Responsibility（职责）** | "a contract or obligation of a classifier" —— 分为**做**（doing）与**知道**（knowing）两类，是实现为方法的义务 | 日常语境里"职责"≈ 岗位分工；这里是可被分配到类上的、可论证的契约 |
| **RDD（职责驱动设计）** | 把软件理解为"一群有职责的角色在协作"的社区隐喻 | 不同于常见的"类=数据结构+方法"视角，RDD 先问"谁该负责"再问"怎么做" |
| **GRASP** | General Responsibility Assignment Software Patterns，九个基础职责分配模式的助记工具 | 不是 GoF 那种代码级设计模式，而是**分配决策的判据**；作者明说名字本身不重要，是"学习辅助" |
| **Information Expert（信息专家）** | 把职责分配给**拥有完成该职责所必需信息**的那个类 | 常被误读为"放到数据最多的类"；作者强调这是避免分散知识的手段，不是就近原则 |
| **Low Coupling / High Cohesion** | 耦合=元素间依赖/知悉/依赖强度；内聚=职责相关且聚焦的程度 | 这两个不是"可选项"而是**评判其他所有 GRASP 决策的元标准**，常作为 Expert 不适用时的裁决依据 |
| **Controller** | UI 层之外第一个接收并协调系统操作的对象（如 Register） | 不是 MVC 的 C 的泛称；特指**用例处理器/外观控制器**这一层 |
| **Pure Fabrication（纯虚构）** | 为了让设计满足高内聚低耦合而**凭空造出来的、领域里不存在**的类（如 RDBOperations） | 反直觉：OO 设计追求"映射现实"，这里却鼓励造非现实的类来救场 |
| **Protected Variations（受保护变化）** | 识别**预测的变化点/不稳定点**，用稳定接口把它们包起来，使变化不外溢 | 是 OCP 在本书里的具体叫法，但更强调"先主动识别变化点"这个动作 |
| **Variation point / Evolution point** | 变化点=当前已存在的多种变体（如多个税率计算器接口）；演化点=未来**可能出现**但当前不存在的新变体 | 两者的区分决定了该"现在就抽象"还是"等它出现再说" |
| **Domain Model（领域模型）** | 领域中值得注意的**概念类**的可视化表示，是"视觉词典"，属于概念视角 | 关键差异：**不是**软件类图，不定义方法，不直接映射成代码 |
| **Architectural Factor（架构因素）** | 对架构有显著影响的 FURPS+ 需求（含可靠性、进度、技能、成本约束） | 超出一般"非功能需求"范围——连"团队技能不足""工期紧"都被算作架构因素 |
| **Use Case Realization（用例实现）** | 描述某个用例在 Design Model 中如何由一组协作对象来实现 | 是设计与需求之间的**对齐单元**，也是本书展开设计讲解的基本颗粒 |

### 核心命题 (用自己的话)

1. 会画 UML ≠ 会做 OO 设计；设计能力来自原则训练，不来自工具或 notation。
2. "这个方法放哪个类"是有正确答案的决策，答案由信息拥有者（Expert）与耦合/内聚后果共同决定。
3. 职责分配过程中的每一步都应当能说出理由——说不出理由的设计就是"magic"，是不可接受的。
4. 领域模型只服务于理解与沟通，没有唯一正确版本；它的价值在于抓住"值得注意"的概念，不在于完备。
5. 把东西错当成属性而不是类，是领域建模最常见的错误；判据是"它是否需要被独立引用/是否有自己的行为"。
6. 设计的核心防御动作是**主动找变化点并用稳定接口隔离它**——这是 GRASP 里最上位、最能派生其他模式的一条。
7. GoF 模式不是要背的 23 个招式，而是几条基本 GRASP 原则在不同场景下的具体化身（常用的约 15 个）。
8. 架构工作的难点不在罗列需求，而在**问对问题**和**权衡取舍**；因素表把"科学"部分工程化，剩下的"艺术"靠经验。
9. 分层只解决"大块怎么分"，块与块之间怎么通信要靠 Facade / Observer / Controller 等微观模式；从上层往下通信要用 Observer 而非反向依赖。
10. 迭代开发的真正机制是**故意在早期引爆变化**，用早期编程/测试/演示换取后期的稳定目标与可靠估算。
11. 框架设计的关键是"把变化的部分留成钩子，把不变的部分固化成算法骨架"（Template Method 是典型手段）。
12. 好架构图是"挑少量有教益的元素讲清大想法"，而不是穷举所有类型。

### 论证链

作者的论证路径是**教学式累积**而非纯演绎：

1. 先建立问题感 —— "给你需求和领域模型，然后给类加方法"这种常见建议是没用的（17 章导言）。
2. 提供替代心智模型 —— RDD：对象是承担职责的协作者。
3. 给出判据 —— GRASP 九模式，每个用统一的 Problem / Solution / 讨论结构，配两个案例反复演练。
4. **用"反例式讲解"建立可信度** —— 作者大量展示"我当时也可以这样设计，但因为耦合/内聚所以没这么做"，把决策过程摊开（18 章刻意"详尽解释以证明没有 magic"）。
5. 抬升抽象层级 —— 证明 GoF 模式可由 GRASP 推导（26.2），让读者不必死记。
6. 放大到系统级 —— 从对象级职责 → 架构因素 → 分层与块间协作。
7. 综合应用 —— Ch38 用持久层框架做一次"多模式协同"的完整演示。

证据形式：**贯穿式案例的复现推理**（NextGen POS 反复迭代三轮，Monopoly 并行演示），加上作者自述的咨询经历（9.3 讲 90 年代 Smalltalk 殡葬系统项目的故事）作为可信度支撑。

## 3. 批判 (Critical) ★

### 作者的时代局限

1. **流程载体（UP/RUP）已整体退场**。全书所有流程建议挂在 Unified Process 的 phase / discipline / artifact 词汇上。UP 在本书出版后几年内迅速被 Scrum、Kanban、XP 等轻量方法取代。剥离 UP 外壳后方法论依然成立，但那套词汇今天已近乎死语，直接照搬会造成沟通障碍。
2. **UML 建模的性价比假设已经失效**。作者在 12.3 专门自辩"这些建模其实只要几小时"，恰恰暴露了当时的争议。今天主流团队默认不做 SSD、操作契约、交互图这个量级的前置建模——不是因为它们错，而是因为迭代周期（周→天）与交付节奏变了。**书里相当篇幅花在 artifact 的制作规程上，这部分折旧最重。**
3. **技术栈锁定在 2004 年的 Java / Swing / 关系数据库**。Ch38 作者自己写了 "Don't Try This at Home!"——Hibernate 已经解决了持久层问题，别自己造。今天 ORM、DI 容器、微服务框架把书中大量"模式应用"变成了框架默认行为：Singleton 变成容器作用域，Template Method 变成框架回调，Facade 变成网关。**按书里的方式手写这些，在今天往往是过度设计。**

### 作者的立场盲点

4. **与 DDD 的合流缺失**。Eric Evans 的《领域驱动设计》与本书几乎同期（2003）。本书的领域模型停在"概念类 + 关联 + 属性 + Description 类"这一层，没有聚合根、限界上下文、统一语言这类**结构性约束与边界划分**。对复杂业务系统而言，单靠 GRASP 做对象级职责分配不足以控制复杂度——它缺了战略设计那一半。
5. **未证假设：对象分解是默认最优分解**。全书默认 OO 是唯一范式，对函数式、数据流、Actor 模型等替代方案未作讨论。"职责分配"这种问法本身就预设了"有状态的、可指派职责的实体"；在纯函数/不可变数据管道里，这套判据的形式完全不同（虽然"隔离变化点"的精神仍然成立）。

### 未被证明的假设

6. **"原则可命名 ⇒ 决策可论证 ⇒ 新手可学会"这一链条的第二段被作者反复强调但未严格验证**。作者的论证方式是"我把我的推理过程摊开给你看"（No-Magic Zone），这展示了**专家事后合理化**的能力，不等于证明了新手能**事前复现**同样的决策。书中也承认"练习久了这些原则会内化到近乎潜意识"（18 章导言）——这恰恰说明熟练度仍靠练习量，而非靠掌握模式名称。
7. **案例的人造性**。NextGen POS 与 Monopoly 都是为教学裁剪过的：作者自己说案例聚焦 domain layer，UI 与 service layer 从略（18.1 注）。真实系统里的脏约束——遗留系统集成、数据迁移、团队认知负载、跨团队协作成本——在案例里被系统性地略过了。**这会让读者低估"技术正确但组织上推不动"的情况。**

### 反对意见（最强的反驳会是什么）

> "把 OO 设计原则体系化到九个 GRASP 模式，是把一件本质上依赖**领域经验与审美判断**的事情包装成可检查的清单。真正的架构能力来自见过足够多的系统失败，而不是记住 Information Expert。而且二十年后的工程实践（框架化、服务化、类型系统演进）已经把这些模式的大多数应用场景吸收进了工具链，继续显式应用它们反而是退步。"

**这个反驳有力但要打折**：GRASP 里最上位的两条——**Protected Variations（主动识别变化点）**与**Low Coupling / High Cohesion（作为元判据）**——并没有被工具链吸收，它们仍然是今天做设计决策时最实用的两个思维动作。折旧的是**表达形式**（UML 图、UP 术语、手写框架），不是**判断力训练**。
